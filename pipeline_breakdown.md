## 2. Подготовка данных

После получения отзывов программа переводит их в единый формат, пригодный для дальнейшего анализа. Этот этап нужен для того, чтобы независимо от источника данных система работала с одинаковой структурой таблицы и не ломалась из-за пропусков, пустых строк или нестандартных названий столбцов.

### Где это реализовано

- первичная подготовка после парсинга: `review_parser/extractors.py:43`
- нормализация структуры перед анализом: `analysis_helpers/pipeline.py:59`
- нормализация меток тональности: `analysis_helpers/pipeline.py:43`

### Как это работает

#### 1. Очистка и первичная валидация отзывов

Если отзывы загружаются из внешнего источника или собираются из ручного ввода, то сначала они проходят через функцию `prepare_reviews(...)`. На этом шаге:

- очищается текст от лишних пробелов и служебных символов;
- отбрасываются слишком короткие или “шумовые” фрагменты;
- сохраняются основные поля:
  - `text`
  - `source`
  - `category`
  - `rating`
  - `date`
- при наличии добавляются идентификаторы и ссылки:
  - `uid`
  - `url`
  - `link`
  - `review_id`

**Ключевой фрагмент:**
- `review_parser/extractors.py:43`
- `review_parser/extractors.py:127`

**Пример листинга:**

```python
def prepare_reviews(
    reviews: list[dict],
    source: str,
    limit: int | None = None,
    min_len: int = 20,
```

```python
def ensure_review_columns(data: pd.DataFrame) -> pd.DataFrame:
    prepared = data.copy()
    if "text" not in prepared.columns:
        text_candidates = [column for column in prepared.columns if prepared[column].dtype == "object"]
        if not text_candidates:
            raise ValueError("В наборе данных нужен столбец с текстом отзыва.")
        prepared = prepared.rename(columns={text_candidates[0]: "text"})
```

- `neutral`

## 3. Анализ тональности

После подготовки данных программа определяет эмоциональную окраску каждого отзыва. На этом этапе для каждого текста вычисляются два основных результата:

- `predicted_sentiment` — предсказанная тональность;
- `confidence` — уверенность модели в этом предсказании.

В текущей версии проекта основным методом анализа является трансформерная модель **RuBERT tiny**, подключённая через библиотеку `transformers`.

## 4. Извлечение аспектов

После определения общей тональности каждого отзыва программа переходит к более детальному анализу содержания. На этом этапе из текстов выделяются **аспекты** — слова или термины, которые обозначают конкретные свойства объекта оценки, например доставку, упаковку, сервис или функциональность товара.

В проекте используется лёгкий эвристический алгоритм, который работает на уровне токенов, частот и частей речи. Это позволяет получать интерпретируемые аспекты без обучения отдельной модели.

#### 3. Нормализация токенов и фильтрация по части речи

Для аспектного анализа допускаются в основном **существительные**, так как именно они чаще всего обозначают предметы оценки. Допустимые части речи задаются в виде множества `ALLOWED_ASPECT_POS = {"NOUN"}`.

Если морфологический анализатор недоступен, используется упрощённая эвристика, которая отсекает часть явно прилагательных форм по окончаниям.

**Ключевой фрагмент:**

**Пример листинга:**

```python
def normalize_token(token: str) -> tuple[str, str | None]:
    morph = get_morph_analyzer()
    if morph is None:
        return token.lower(), None
    parsed = morph.parse(token.lower())[0]
    return parsed.normal_form, parsed.tag.POS
```

#### 4. Отсев стоп-слов и слишком общих терминов

Чтобы в список аспектов не попадали общеязыковые или слишком абстрактные слова, программа использует специальный набор `ASPECT_STOPWORDS`. В него включены:

- служебные слова;
- усилители и вводные слова;
- слишком общие для отзывов термины;
- слова, которые не несут полезной аспектной нагрузки.

Например, из рассмотрения исключаются слова вроде:

- `отзыв`

## 5. Построение аспектной статистики

После того как для каждого отзыва определён список аспектов, программа переходит от индивидуального уровня к агрегированному. На этом этапе рассчитывается **сводная статистика по аспектам**, которая показывает:

- сколько раз аспект упоминался;
- с какими тональностями он связан;
- какова доля негативных упоминаний.

Именно этот этап даёт основу для вкладки с аспектами в расширенном анализе: диаграмм, таблиц проблемных аспектов и карточек по выбранному аспекту.

### Где это реализовано

- построение аспектной статистики: `analysis_helpers/pipeline.py:152`
- подключение этапа к общему пайплайну: `analysis_helpers/pipeline.py:131`

- `review_id`
- `aspects`
- `predicted_sentiment`

- название аспекта;
- предсказанную тональность отзыва;
- идентификатор отзыва.

То есть таблица вида “один отзыв — много аспектов” преобразуется в таблицу вида “одно упоминание аспекта — одна строка”.

**Ключевой фрагмент:**
- `analysis_helpers/pipeline.py:153`

- строки соответствуют аспектам;
- столбцы соответствуют классам тональности;
- значения показывают, сколько раз аспект встречался в отзывах соответствующей тональности.

Таким образом для каждого аспекта отдельно подсчитываются:

- число позитивных упоминаний.

Так как в конкретной выборке может не встретиться одна из тональностей, программа отдельно проверяет наличие всех трёх столбцов:

- `negative`
- `neutral`
- `positive`

Такой подход особенно важен для интерфейса и экспортов: таблицы и диаграммы ожидают одинаковый набор колонок даже в случае полностью позитивной или полностью негативной выборки.

## 6. Тематическое моделирование

После построения аспектной статистики программа пытается выделить в отзывах более крупные **смысловые темы**. Если аспекты показывают отдельные предметы оценки, то темы позволяют ответить на вопрос: **о чём в целом пишут пользователи**.

В проекте для этого используется алгоритм **LDA** (`Latent Dirichlet Allocation`), который выделяет скрытые тематические структуры в корпусе текстов.

### Где это реализовано

- подготовка тематических данных и формирование итоговых таблиц: `analysis_helpers/pipeline.py:182`
- построение модели LDA: `analysis_helpers/topics.py:26`
- извлечение ключевых слов темы: `analysis_helpers/topics.py:42`

### Как это работает

#### 1. Выбор входных данных для тематического анализа

Программа не всегда подаёт в тематическую модель исходные тексты отзывов напрямую. Сначала она пытается использовать **аспектные представления**, то есть объединённые списки аспектов для каждого отзыва.

Такой подход делает тему более интерпретируемой, потому что модель работает уже не по полному тексту, а по выделенным содержательным терминам.

Если же аспектных данных оказывается слишком мало, программа автоматически переключается на исходные тексты отзывов.

**Ключевой фрагмент:**
- `analysis_helpers/pipeline.py:188`

**Пример листинга:**
```python

if sum(bool(text.strip()) for text in topic_input) < 3:
    topic_input = reviews["text"].tolist()
```

#### 2. Нормализация текста перед тематическим анализом

Перед подачей в `CountVectorizer` каждый текст проходит через специальный анализатор `_topic_analyzer(...)`. Он:

- токенизирует текст;
- нормализует слова;
- удаляет слишком короткие токены;
- удаляет тематические стоп-слова;
- дополнительно добавляет биграммы из соседних слов.

За счёт этого модель видит не только отдельные слова, но и устойчивые сочетания, что делает темы более осмысленными.

**Ключевой фрагмент:**
- `analysis_helpers/topics.py:7`

**Пример листинга:**
```python
def _topic_analyzer(text: str) -> list[str]:
    normalized_tokens: list[str] = []
    for token in tokenize(text):
        normalized, _ = normalize_token(token)
        if len(normalized) < 3:
            continue
        if normalized in TOPIC_STOPWORDS:
            continue
        normalized_tokens.append(normalized)

    tokens = normalized_tokens[:]
    tokens.extend(
        f"{left} {right}"
        for left, right in zip(normalized_tokens, normalized_tokens[1:])
        if left != right and left not in TOPIC_STOPWORDS and right not in TOPIC_STOPWORDS
    )
    return tokens
```

#### 3. Векторизация корпуса

Для тематического моделирования тексты сначала переводятся в матрицу частот терминов с помощью `CountVectorizer`. В отличие от кластеризации, здесь используется не `TF-IDF`, а обычное мешковое представление слов, что лучше соответствует классической постановке LDA.

При этом параметры векторизатора подстраиваются под размер корпуса:

- если отзывов мало, используется более мягкий порог `min_df`;
- если отзывов больше, редкие слова отсекаются строже.

**Ключевой фрагмент:**
- `analysis_helpers/topics.py:31`

**Пример листинга:**
```python

vectorizer = CountVectorizer(analyzer=_topic_analyzer, max_df=0.9, min_df=min_df)
X = vectorizer.fit_transform(texts)
```

Хотя по умолчанию программа ориентируется на `5` тем, реальное число компонент ограничивается размерами корпуса и словаря. Это защищает модель от ошибок в случаях, когда:

- отзывов слишком мало;
- словарь оказался слишком узким;
- число документов или признаков меньше запрошенного числа тем.

Поэтому программа вычисляет `actual_topics` как минимум из:

- желаемого числа тем;
- числа документов;
- числа признаков.

**Ключевой фрагмент:**
- `analysis_helpers/topics.py:35`

**Пример листинга:**

Чтобы сделать темы интерпретируемыми, программа отдельно извлекает для каждой темы набор наиболее значимых терминов. Для этого анализируются веса слов в матрице компонентов LDA.

- `top_words = 8`

**Ключевой фрагмент:**
- `analysis_helpers/topics.py:42`

**Пример листинга:**

```python
def describe_topics(lda, vectorizer, top_words=8):
    feature_names = vectorizer.get_feature_names_out()
    rows = []
    for topic_idx, topic in enumerate(lda.components_):
        top_indices = topic.argsort()[:-(top_words + 1):-1]
        for word_idx in top_indices:
            rows.append(
                {
                    "topic": f"Тема {topic_idx + 1}",
                    "term": feature_names[word_idx],
                    "weight": round(float(topic[word_idx]), 4),
                }
            )
    return pd.DataFrame(rows)
```

## 7. Кластеризация отзывов

После тематического моделирования программа дополнительно группирует отзывы по **лексическому сходству**. Если темы отвечают на вопрос, о чём пишут пользователи, то кластеризация помогает понять, **какие отзывы похожи друг на друга по используемым словам и выражениям**.

В проекте для этого используется связка:

- `TF-IDF` для векторизации текстов;
- `K-Means` для разбиения отзывов на группы.

### Где это реализовано

- построение кластеров: `analysis_helpers/pipeline.py:239`
- константа случайного состояния: `analysis_helpers/config.py:1`
- подключение этапа к общему пайплайну: `analysis_helpers/pipeline.py:135`

### Как это работает

#### 1. Проверка достаточности выборки

Перед запуском кластеризации программа оценивает размер набора отзывов. Если отзывов меньше трёх, полноценная кластеризация считается нецелесообразной, и всем записям присваивается один общий кластер.

Это позволяет избежать нестабильных результатов на слишком маленькой выборке.

**Ключевой фрагмент:**
- `analysis_helpers/pipeline.py:244`

**Пример листинга:**
```python
_check_cancel(cancel_check)
if len(reviews) < 3:
    return ["Кластер 1"] * len(reviews)
```

#### 2. Определение числа кластеров

По умолчанию программа ориентируется максимум на `5` кластеров, но реальное число кластеров не может превышать число отзывов. Поэтому вычисляется:

- `n_clusters = min(max_clusters, len(reviews))`

Такой подход предотвращает ошибки, когда количество групп оказывается больше числа наблюдений.

**Ключевой фрагмент:**
- `analysis_helpers/pipeline.py:248`

**Пример листинга:**
```python
n_clusters = min(max_clusters, len(reviews))
```

#### 3. Векторизация текстов с помощью TF-IDF

Чтобы применить кластеризацию, отзывы сначала нужно перевести из текстовой формы в числовое представление. Для этого используется `TfidfVectorizer`, который строит матрицу признаков на основе:

- отдельных слов (`unigram`);
- пар соседних слов (`bigram`).

В текущей реализации используются параметры:

- `max_features = 1000`
- `ngram_range = (1, 2)`

Это позволяет одновременно учитывать и отдельные важные слова, и устойчивые словосочетания.

**Ключевой фрагмент:**
- `analysis_helpers/pipeline.py:249`

**Пример листинга:**
```python
vectorizer = TfidfVectorizer(max_features=1000, ngram_range=(1, 2))
matrix = vectorizer.fit_transform(reviews["text"])
```

#### 4. Построение модели K-Means

После векторизации на полученную матрицу признаков обучается модель `KMeans`. Она разбивает отзывы на группы так, чтобы тексты внутри одного кластера были как можно более похожи друг на друга, а тексты из разных кластеров — как можно более различны.

Для повышения воспроизводимости используется фиксированное значение:

- `RANDOM_STATE = 42`

Также явно задано:

- `n_init = 10`

что означает несколько запусков алгоритма с последующим выбором лучшего варианта.

**Ключевой фрагмент:**
- `analysis_helpers/pipeline.py:254`
- `analysis_helpers/config.py:1`

**Пример листинга:**
```python

labels = model.fit_predict(matrix)
```

#### 5. Обработка ошибок кластеризации

Если на этапе построения `TF-IDF`-матрицы или обучения `KMeans` возникает ошибка, программа не прерывает выполнение всего анализа. Вместо этого она возвращает для всех отзывов специальное значение:

- `Кластер не определён`

Это позволяет интерфейсу корректно показать, что кластерная структура не была построена, не ломая остальные разделы анализа.

**Ключевой фрагмент:**
- `analysis_helpers/pipeline.py:250`

**Пример листинга:**
```python
try:
    _check_cancel(cancel_check)
    matrix = vectorizer.fit_transform(reviews["text"])
    _check_cancel(cancel_check)
    model = KMeans(n_clusters=n_clusters, random_state=RANDOM_STATE, n_init=10)
    labels = model.fit_predict(matrix)
except ValueError:
    return ["Кластер не определён"] * len(reviews)
```

#### 6. Формирование человекочитаемых меток

После того как модель присвоила каждому отзыву числовой номер кластера, программа переводит эти значения в удобные для отображения текстовые метки:

## 8. Вычисление метрик качества и матрицы ошибок

После завершения основных аналитических этапов программа, при наличии эталонных меток, оценивает качество работы модели тональности. Этот этап нужен для того, чтобы не только показать результат классификации, но и количественно оценить, насколько предсказания согласуются с ожидаемыми значениями.

В проекте рассчитываются:

- `accuracy`;
- `precision`;
- `recall`;
- `F1`;
- матрица ошибок;
- таблица представления метрик по модели.

### Где это реализовано

- построение матрицы ошибок: `analysis_helpers/pipeline.py:219`
- построение таблицы сравнения модели: `analysis_helpers/pipeline.py:231`

### Как это работает

#### 1. Проверка наличия эталонных меток

Метрики качества вычисляются только в том случае, если у отзывов есть столбец `label`. Эти метки могут:

- присутствовать во входном наборе данных изначально;
- быть восстановлены ранее из числового рейтинга.

Если `label` отсутствует, программа не пытается считать метрики и возвращает пустой словарь.

**Ключевой фрагмент:**
- `analysis_helpers/pipeline.py:97`
- `analysis_helpers/pipeline.py:124`

**Пример листинга:**
```python

if labels is not None and method == "transformer":
    metrics = evaluate(labels, reviews["predicted_sentiment"].tolist())
elif labels is None:
    metrics = {}
```

#### 2. Сравнение истинных и предсказанных меток

Если эталонные значения доступны, программа сравнивает:

- `true_labels` — истинные метки из `label`;
- `pred_labels` — предсказания модели из `predicted_sentiment`.

Для этого используется функция `evaluate(...)`, внутри которой вызываются стандартные метрики из `scikit-learn`.

**Ключевой фрагмент:**
- `analysis_helpers/evaluation.py:3`

**Пример листинга:**
```python
def evaluate(true_labels, pred_labels):
    return {
        "accuracy": accuracy_score(true_labels, pred_labels),
        "precision": precision_score(true_labels, pred_labels, average="weighted", zero_division=0),
        "recall": recall_score(true_labels, pred_labels, average="weighted", zero_division=0),
        "F1": f1_score(true_labels, pred_labels, average="weighted", zero_division=0),
    }
```

#### 3. Почему используются weighted-метрики

Для `precision`, `recall` и `F1` применяется режим:

- `average="weighted"`

Это означает, что вклад каждого класса в итоговую метрику учитывается с поправкой на его частоту в выборке. Такой подход особенно полезен для отзывов, где классы `negative`, `neutral` и `positive` могут быть распределены неравномерно.

Также задано:

- `zero_division=0`

что позволяет избежать ошибок в ситуациях, когда для какого-либо класса не удаётся корректно вычислить частные показатели.

#### 4. Построение матрицы ошибок

Кроме сводных метрик программа строит матрицу ошибок, показывающую, как именно распределяются совпадения и ошибки классификации между классами.

Строки матрицы соответствуют:

- истинным меткам;

а столбцы:

- предсказанным меткам.

Если столбца `label` нет, матрица ошибок не строится и возвращается пустая таблица.

**Ключевой фрагмент:**
- `analysis_helpers/pipeline.py:219`

**Пример листинга:**

## 10. Визуализация результатов в кратком и расширенном режимах

После фильтрации программа переходит к основному пользовательскому сценарию — отображению результатов анализа в интерфейсе. На этом этапе данные преобразуются в **метрики, диаграммы, таблицы и исследовательские представления**, которые позволяют быстро оценить общий фон отзывов и при необходимости перейти к более детальному разбору.

Визуализация в проекте разделена на два уровня:

- **краткий обзор** — быстрый срез состояния набора отзывов;
- **расширенный анализ** — детальное исследование аспектов, тем, кластеров, периодов и отдельных записей.

### Где это реализовано

- основной сценарий показа вкладок: `streamlit_app.py:116`
- краткий обзор: `ui/dashboard/pages.py:91`
- расширенный анализ: `ui/dashboard/pages.py:317`
- отдельные исследовательские представления: `ui/dashboard/research.py:20`

### Как это работает

#### 1. Отображение кратких сводных метрик

Перед построением больших диаграмм интерфейс показывает пользователю компактную сводку по текущей выборке. На этом уровне выводятся:

- количество отзывов после фильтрации;
- средняя уверенность модели;
- средняя длина отзывов;
- число негативных отзывов;
- имя используемой модели.

Эти значения помогают сразу понять масштаб выборки и общий характер данных ещё до перехода к детальному анализу.

**Ключевой фрагмент:**
- `ui/dashboard/components.py:154`

**Пример листинга:**

## 11. Формирование отчёта и экспорт результатов

Этот этап важен тем, что переводит результаты анализа из интерактивного интерфейса в автономные артефакты, которые можно передавать, архивировать и сравнивать между собой.

- сохранять историю запусков.

Также программа автоматически удаляет старые лог-файлы, оставляя только последние `20`.

**Пример листинга:**

#### 4. Отмена длительных операций пользователем

В интерфейсе предусмотрена кнопка `Отменить операцию`, которая становится доступной только в момент реально выполняющейся длительной операции. При нажатии программа:

Если отмена обнаружена, выбрасывается исключение `RuntimeError("Операция отменена пользователем.")`, которое затем перехватывается на верхнем уровне.

#### 7. Обработка ошибок импорта по ссылке

Если при URL-импорте возникает ошибка, программа различает по меньшей мере два сценария:

- отмена пользователем;
- обычная ошибка загрузки или извлечения отзывов.

В первом случае:

- операция помечается как завершённая;
- прогресс очищается;
- выводится предупреждение;
- выполнение страницы останавливается корректно.

Во втором случае:

- ошибка записывается в лог;
- пользователю показывается сообщение `Не удалось загрузить отзывы`;
- дополнительно выводится пояснение о возможных причинах, например о динамической загрузке данных сайтом.

**Ключевой фрагмент:**
- `ui/dashboard/pages.py:42`

**Пример листинга:**
```python
except RuntimeError as exc:
    set_operation_running(False)
    progress_placeholder.empty()
    st.session_state.pop("pending_url_import", None)
    st.warning(str(exc))
    st.stop()
except Exception as exc:

    logger.exception("URL import failed: %s", exc)
    progress_placeholder.empty()
```

#### 8. Защита от ошибок анализа

Аналогичная логика применяется и к основному этапу аналитической обработки. Запуск анализа обёрнут в конструкцию `try/except/finally`, что позволяет:

- отделить штатную отмену от реальной ошибки;
- гарантированно сбрасывать флаг `operation_running`;
- очищать состояние отмены после успешного завершения.

Это делает поведение программы предсказуемым даже при сбоях в аналитическом модуле.

**Ключевой фрагмент:**
- `streamlit_app.py:78`

**Пример листинга:**
```python
try:
    set_operation_running(True)
    result = run_analysis_from_frame(
        active_frame,
        active_method,
        cancel_check=is_cancel_requested,
    )
except RuntimeError as exc:
    logger.warning("Operation cancelled: %s", exc)
    clear_cancel()
    st.warning(str(exc))
    st.stop()
except Exception as exc:
    logger.exception("Analysis failed: %s", exc)
    st.error(f"Не удалось выполнить анализ: {exc}")
    st.stop()
finally:
    set_operation_running(False)
    if not is_cancel_requested():
        clear_cancel()
```
